4. Агент будет работать поэтапно и после каждого этапа отчитываться. В конце проверьте продукт по чек-листу «Приёмка» (он в конце промпта) — для проверки не нужно уметь программировать.

Прежде чем писать код, полностью прочитай файл `CK3-Localization-Manager-Spec.md` в корне этой папки. Это единственный источник истины по требованиям. Правила приоритета:

- Неоднозначность → решай в духе раздела 3 спецификации («Железные принципы») и раздела 20 («Решения, принятые клиентом»).
- Что-то реализовать невозможно или требования противоречат друг другу → не выдумывай молча обходной путь: остановись, опиши проблему простыми словами и предложи вариант решения.

## 1. Железные правила (нарушать нельзя ни при каких условиях)

1. **Файлы автора мода в `steamapps\workshop\content\1158310` никогда не изменяются и не удаляются.** Приложение только ДОБАВЛЯЕТ собственные папки/файлы локализации. База приложения — источник истины: всё записанное восстановимо из неё.
2. **Для файлов локализации CK3 — только собственный построчный lossless-парсер.** Никаких YAML-библиотек (PyYAML, ruamel и т.п.) для этих файлов. Тест «прочитал → записал без изменений → байт в байт совпало» обязателен и должен проходить на всём тестовом корпусе.
3. **Игровые коды** (`$...$`, `[...]` с вложенностью, `@...!`, парные `#X ... #!`, литеральный `\n`) защищаются лексером до любого машинного перевода и валидируются после. Строка с повреждёнными кодами в запись не попадает.
4. **Машинный перевод получает статус «не проверен»**, это отдельный статус от «проверено человеком».
5. **Единица учёта — ключ локализации** (не файл). Дубликаты ключей, расхождения имени/пути/заголовка, «лишние» ключи целевого языка → диагностика для человека, не автоисправление.
6. **Любая запись на диск атомарна**: временный файл → проверка → резервная копия старого → замена. Выходные файлы локализации — UTF-8 с BOM.
7. **Секреты (API-ключи) — только в Windows Credential Manager** через `keyring`. Никогда в файлах настроек, коде или базе.
8. **Никаких неофициальных обёрток переводчиков** (googletrans и подобные) — только официальные API.
9. **Все пути обрабатываются как Unicode** — у пользователя папки с кириллицей в именах (например `C:\Users\...\Desktop\Проекты\...`). Это должно быть покрыто тестами.

## 2. Технологии и структура

- Python 3.12+, GUI — PySide6, база — SQLite (через stdlib `sqlite3`), HTTP — `httpx`, слежение за папками — `watchdog` (с debounce), секреты — `keyring`, сборка в exe — PyInstaller.
- Структура проекта:

```
ck3loc/
├── core/          # парсер, сканер, снимки, diff, статусы, лексер кодов,
│                  # форматы (JSONL, XLIFF), запись перевода, восстановление
├── providers/     # base + google, yandex, deepl, llm (OpenAI-совместимый + Claude),
│                  # опционально azure, argos; external (файловый обмен)
├── cli/           # все операции ядра доступны из командной строки
├── desktop/       # PySide6-интерфейс
└── tests/
    └── fixtures/  # тестовый корпус файлов локализации
```

- Ядро (`core/`) не импортирует ничего из `desktop/`. Всё, что умеет GUI, умеет и CLI — это проверяется тестами.
- Язык интерфейса — русский. Тексты интерфейса вынесены так, чтобы позже можно было добавить другие языки UI.
- Логи пишутся в файл в папке данных приложения; сообщения об ошибках для пользователя — человеческие, без трейсбеков.

## 3. Порядок сборки и ворота приёмки

Работай строго по этапам. После каждого этапа: прогони ВСЕ тесты, убедись, что они зелёные, и напиши краткий отчёт (что сделано, как проверено). Не переходи к следующему этапу с падающими тестами.

### Этап 1 — Lossless-парсер + тестовый корпус

- Построчный парсер: узлы «заголовок языка», «запись» (отступ, ключ, необязательное число после двоеточия, сырое значение, декодированное значение, хвост строки), «комментарий», «пустая строка», «нераспознанная строка». Нераспознанные строки сохраняются как есть и помечаются в диагностике.
- Создай синтетический корпус в `tests/fixtures/`, покрывающий: UTF-8 BOM и без BOM; CRLF и LF; `key:0 "..."` и `key: "..."`; комментарии (в т.ч. в конце строки значения); пустые строки; экранированные кавычки; `\n` в значении; игровые коды всех видов; вложенные папки; обе формы replace (`localization/replace/russian/` и `localization/russian/replace/`); дубликаты ключей; битые строки; файл, где путь говорит «russian», а заголовок — `l_english`.
- Напиши `tools/make_fixtures.py`: если на машине найден Steam, скрипт копирует (только чтение!) локализации нескольких реальных модов в `tests/fixtures/real/` для локального прогона.
- **Ворота:** тест round-trip «байт в байт» проходит на всём корпусе.

### Этап 2 — Сканер (только чтение)

- Поиск Steam: реестр Windows → `steamapps/libraryfolders.vdf` → все библиотеки на всех дисках → `workshop/content/1158310`. Ручное указание пути как запасной вариант.
- Разбор `descriptor.mod` (name, version, supported_version, remote_file_id). Название из Steam Workshop API по ID — как fallback и дополнение; при отсутствии интернета всё работает, просто без воркшопных названий.
- Определение языков, подсчёт файлов и ключей, полнота каждого языка относительно источника, диагностика (раздел 10 спецификации).
- Поиск установленной CK3 и индексация ванильной локализации (английский + русский минимум).
- **Ворота:** команды `ck3loc scan` (сводка по библиотеке) и `ck3loc report <mod_id>` (полный отчёт по моду со списком пропущенных ключей) работают на реальной библиотеке.

### Этап 3 — База, снимки, сравнение версий

- Схема SQLite по разделу 15 спецификации. Снимки локализации каждой замеченной версии мода (разобранные ключи-значения + сжатые копии изменившихся файлов).
- Составной отпечаток версии мода (раздел 9): время обновления Steam (+ чтение `appworkshop_1158310.acf` как локального сигнала), хеш локализации (семантический, по значениям ключей), хеш дерева (фоново).
- Трёхстороннее сравнение и полный автомат статусов из раздела 7: актуален / устарел / конфликт / осиротел / не переведён / без истории + все флажки.
- **Ворота:** тестовый сценарий: изменить копию мода (добавить/изменить/удалить ключи) → приложение точно перечисляет изменения и правильно выставляет статусы. Хеш значения не меняется от перестановки строк и комментариев — есть тест.

### Этап 4 — MVP: обмен файлами, запись перевода, первый GUI

- Экспорт JSONL (раздел 13.1) c генерацией промпта-инструкции для LLM; строгий импорт (менять можно только `target`; проверка id/key/source, защитных маркеров, актуальности источника; отчёт о принятых/отклонённых). Экспорт/импорт XLIFF 2.1. Человекочитаемый предпросмотр (Markdown) — только на чтение.
- Запись перевода, оба режима из раздела 5: **«внутрь мода»** (по умолчанию: добавление `localization/russian/`, зеркальные имена файлов; переопределения — в `localization/replace/russian/`) и **«отдельный патч-мод»** (структура и descriptor из раздела 5.2, манифест `.ck3loc/manifest.json`). Режимы сборки: полный / дельта, автоопределение.
- Восстановление: при сканировании обнаруживается пропажа записанных файлов (Steam обновил мод) и расхождения с базой (ручные правки) → сценарии D, G, H спецификации.
- GUI: главный экран со сводкой и таблицей модов (раздел 14.1), карточка мода с вкладками (14.2), таблица строк с фильтрами (14.3, пока без встроенного API-перевода), экспорт/импорт, центр уведомлений (14.4).
- **Ворота (MVP):** сквозной сценарий B из спецификации проходит целиком: мод без русского → экспорт JSONL → перевод во внешней LLM → импорт → запись в мод → файлы корректны (валидны, UTF-8 BOM, коды целы) и игра их читает.

### Этап 5 — Встроенный перевод

- Единый интерфейс провайдера. Волна 1: Google Cloud Translation, Yandex Translate, DeepL. Волна 2: LLM по API (OpenAI-совместимый endpoint + Anthropic), с настраиваемым промптом, глоссарием и контекстом типа строки (`*_desc` → описание и т.п.). Опционально: Azure, Argos (офлайн). Пакетирование под лимиты API, повторы при сбоях, продолжение прерванного.
- Конвейер перед API: ванильная локализация CK3 → память переводов (точное совпадение) → похожие строки (только подсказка) → API. Защита кодов (правило 3) на каждой строке.
- Память переводов, глоссарий трёх уровней с режимами (обязательный/предпочтительный/не переводить); стартовый глоссарий CK3 (Realm → Держава, Holding → Владение, County → Графство и другие базовые термины — собери 40–60 штук из ванильной локализации).
- Редактор строки (трёхколоночная панель из 14.3, горячие клавиши), мастер пакетного перевода со сметой до запуска (14.5).
- **Ворота:** сценарии B (через API), C, D, I проходят целиком в GUI.

Функции этапа 6 спецификации (плейсеты, конфликты модов, объединённый пак, публикация в Workshop, анализ error.log) — НЕ делать.

## 4. Приёмка (проверка человеком без навыков программирования)

Подготовь в корне проекта:

- `install.bat` — создаёт окружение и ставит зависимости; `run.bat` — запускает приложение; `run_tests.bat` — прогоняет все тесты и пишет «ВСЕ ТЕСТЫ ПРОЙДЕНЫ» или список упавших.
- `README-запуск.md` на русском: как установить и запустить, как выполнить проверочные сценарии ниже.

Продукт считается принятым, когда заказчик, следуя README, может сам:

1. Запустить `run_tests.bat` → «ВСЕ ТЕСТЫ ПРОЙДЕНЫ».
2. Запустить приложение → оно находит его библиотеку Steam и показывает сводку (сколько модов, сколько без русского).
3. Открыть любой мод без русского → «Создать русский перевод» → экспорт JSONL → перевести файл в любом LLM-чате → импортировать → «Записать перевод» → в папке мода появилась корректная папка `localization/russian/`, в игре — русский текст.
4. Ввести ключ DeepL или Google/Yandex → перевести маленький мод встроенным переводом.
5. Дождаться обновления любого переведённого мода (или сымитировать по README) → приложение сообщает, что изменилось, восстанавливает перевод и предлагает доперевести новое.
